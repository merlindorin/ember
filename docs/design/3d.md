# The 3D API, built like twod

Status: approved, then **on hold** since 2026-10-30. Nothing beyond what exists is built.

The 3D guide section waits on this. Today a game declares its own structs and fills components by hand:

```go
type Cube struct {
	*world.BasicEntity
	scene.Transform
	render.Model
}
cube := &Cube{world.NewBasic(), scene.At(0, 0, 0), render.Model{Mesh: m, Material: &render.Material{Albedo: color.White, Unlit: true}}}
eye := &Eye{world.NewBasic(), scene.At(0, 0, 3).LookingAt(geom.V3(0, 0, 0)), render.Camera{}}
model.Spawn(w, scene.At(0, 0, 0)) // adds itself to the World
```

twod settled the shape: ready-made entities from constructors with typed options, getters of the same name, setters where runtime change is meant (0018, 0019), and `Base`/`Build` for a game's own entities. 3D should read the same:

```go
cube := threed.NewModel(rgbCube(), threed.Material(render.NewMaterial(render.Color(color.White), render.Unlit())))
eye := threed.NewCamera(threed.At(0, 0, 3), threed.LookAt(0, 0, 0))
hero := gltf.NewInstance(model, threed.At(2, 0, 0), threed.Yaw(math.Pi))
w.AddEntities(cube, eye, hero)
```

## Package

- **`ember/threed`** holds the 3D entities, their options and the shared placement, as `twod` does for 2D. It is pure Go and joins the cgo-free list.
- **`render`** keeps what the renderer reads: the components, materials, `Environment`, `Post` and `Effect`. Games reach the components only through getters.
- **`gltf`** builds instances; `node/node3d` keeps the scene classes and moves onto threed's entities later.

## Entities

| Entity | Constructor | Own options | Setters and reads |
|---|---|---|---|
| Model | `NewModel(mesh, …ModelOption)` | `Material(m)`, `Tint(c)`, `NoShadow()` | `SetMesh`, `SetMaterial`, `SetTint` |
| Camera | `NewCamera(…CameraOption)` | `FOV(radians)`, `Clip(near, far)`, `Ortho(height)`, `Priority(n)`, `In(win)`, `Post(p)` | setters for each, `View()`, `Presenting()` |
| PointLight | `NewPointLight(c, …LightOption)` | `Intensity(i)`, `Range(r)`, `Flicker(f)` | setters for each |
| Instance | `gltf.NewInstance(model, …threed.Option)` | | `Part(name)`, `Attach(model, joint, offset)`, `Animator()` |

- **Shared options** (`threed.Option`), on every entity: `At(x, y, z)`, `Rotation(q)`, `Yaw(radians)`, `LookAt(x, y, z)`, `Scale(x, y, z)`, `Hidden()`. Their reads and writes: `Position()`/`SetPosition(p)`, `Rotation()`/`SetRotation(q)`, `Scale()`/`SetScale(s)`, `Translate(d)`, `LookAt(p)` and `Forward()`.
- **Typed options:** `Material` on a camera does not compile, as in twod.
- **Children:** `Add(children…)` returns the parent. A child is placed in its parent's space, which replaces `scene.Attach(w, parent, child)`.
- **The game's own entities:**
  - One that draws embeds a ready-made entity (`*threed.Model`) and adds its own components.
  - One that only has a place embeds `threed.Item` from `threed.Base()` and is finished by `threed.Build(e, name, opts…)`, which names it and applies its options, as in twod.
- **Building and adding:** nothing adds itself to the World. `Model.Spawn(w, t)` goes, `Instance.Attach` loses its `w`, and everything is added with `AddEntities`.
- **Materials:** `render.NewMaterial(…MaterialOption)` takes `Color(c)`, `Emissive(c, intensity)`, `Specular(s)`, `Unlit()`, `Wind(s)`, `Transparent()`, `Texture(t)` and `DoubleSided()`, each with a getter and setter. `Mat` and `Glow` go, so there is one way to make one.
- **Environment:** the options lose their `With`: `Sun`, `Shadows`, `NoShadows`, `Ambient`, `Fog`, `Exposure`, `Bloom`, `Vignette`, `ColorGrade`. `render.Option` becomes `EnvironmentOption`.
- **Cameras that move themselves:** `camera.NewOrbit`/`NewFollow`/`NewFly` already have options. They are built on `threed.Camera` and also take its options (FOV, Clip…).

## Placement

`scene.Transform` keeps its job (the hierarchy, `World()`, the transform system). Its exported fields `Position`, `Rotation` and `Scale` become unexported behind the methods above, as twod's `Placement` did. That is the largest change: anim, camera, net, node3d and the examples write the fields today.

## Steps

1. **threed and materials:** `threed` with Model, Camera and PointLight, `Base`/`Build`, `render.NewMaterial`, the environment renames and `gltf.NewInstance`. Examples 01, 09 and 10 move onto them, with tests per option and setter. The old struct literals still compile in this step.
2. **One way:** the component fields go unexported, along with `scene.Transform`'s fields and `Spawn`, and every caller in ember moves over. One green commit, emberfall left as it is.
3. **Scenes:** node3d's classes are built from threed's entities, with the class names kept so saved scenes still load.

The guide's 3D pages can start after step 1, on the new API.

## Alternatives

- **Constructors in `render`:** no new package, but render would mix the renderer's contract with the game's entities, and `render.NewCamera` beside `camera.NewOrbit` reads oddly. twod's split works.
- **Keep struct literals and document them:** no migration, but it is the opposite of the 2D rules the guide teaches a page earlier, and fields can't validate or be watched.
- **Exported fields alongside getters:** fields named like their getters can't coexist in Go, and two ways to set a position is what 0018 rules out.

## Questions

1. Is `threed` the name, or does 3D take `render`'s place for entities?
2. Should step 2's `scene.Transform` change wait until the scene work in step 3, so the large migration happens once?
3. `SetPosition(geom.Vec3)` or `SetPosition(x, y, z)`? twod's takes a `Vec2`, so this proposes `Vec3`, with `At(x, y, z)` as the option.

## Later

- **world.Time:** all of its fields are writable, so a game can change `Elapsed` or `Frame`, which decision 0019 rules out. When the 3D work resumes, review it into read methods (`Elapsed()`, `RealElapsed()`, `Frame()`, `Alpha()`…) plus `SetScale` and `SetMaxDelta`.
